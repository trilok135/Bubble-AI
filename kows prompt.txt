You read CONTRACT.md before anything else. You build against schema, never against imagined data.

YOUR JOB.
1. Import the existing Stitch UI screens as-is. Do not redesign them.
2. Build ONE adapter file, api/adapter.ts — one function per CONTRACT.md endpoint, named after the path (e.g. getNodes(), getMetricsFull(), postOptimize()). This is the ONLY place a URL or field name is ever typed.
3. BASE_API_URL is one env var. Every adapter function uses it. Nothing else in the app calls fetch directly.
4. Build these components, mapped field-for-field to the schema, no invented props:
   - NodeCard: cpu_pct, ram_pct, latency_ms, status, pheromone (use pheromone value to drive a visual "thickness" or glow on the connection line — this is the sponge-algorithm visual, make it obvious).
   - TrafficGraph: subscribes to /ws/telemetry, plots workloads[].traffic_rps over time.
   - SLABanner: reads node.status, shows healthy/degraded/overloaded per workload's current_node.
   - DecisionLog: lists /decisions/history, shows reasoning field per entry.
5. Before any backend is ready: point every adapter function at a local mock server or static JSON fixture that matches the schema exactly. Build and test the full UI against that first.

LOOP. Do this per component:
1. Take one Stitch screen. List the data fields it displays.
2. Map every field to a CONTRACT.md schema field name. Field not in schema? Add a TODO comment, use a placeholder value, keep going — never block the build on a missing field.
3. Wire the component to the mock fixture via adapter.ts.
4. Render it. Pass -> next component.
5. Crashes -> fix once, retest.
6. Crashes again -> wrap in try/catch, show a fallback "data unavailable" state for that component only, log to BLOCKERS.md, move to next component. Never let one broken component take down the page.
7. All components done -> run full app against mock fixtures. Confirm every screen renders.
8. Write STATUS.md: READY (mock) or PARTIAL. Stop.
