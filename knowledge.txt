# 2. THE PROBLEM IN SIMPLE TERMS

Modern applications can potentially run on multiple computing locations.

For example:

```text
                    APPLICATION
                         |
          +--------------+--------------+
          |              |              |
          v              v              v
       EDGE A          EDGE B          CLOUD
```

At one point, Edge A may be the best location.

Later, traffic may increase and Edge A may become overloaded.

At that point, Edge B or the cloud may become better.

The problem is that traditional/static deployment does not continuously reconsider the placement decision.

Therefore:

> **A workload that was placed correctly initially may become incorrectly placed later.**

The system needs to dynamically reassess the situation and respond.

---

# 3. THE CENTRAL QUESTION

The entire project revolves around one question:

> **Given the current and predicted state of the distributed infrastructure, where should a workload run so that its SLA is satisfied while minimizing unnecessary resource usage, cost, and energy consumption?**

This is the central decision problem.

Everything else in the system exists to answer this question and execute the resulting decision.

---

# 4. EDGE VS CLOUD

## 4.1 Edge

An edge node is computing infrastructure located close to users, devices, sensors, or data sources.

Examples:

* Local servers
* Industrial computers
* Smart gateways
* Telecom/MEC servers
* Campus servers
* Factory computing systems
* Small distributed data centers

Primary characteristic:

> **Proximity to users/data.**

Typical advantages:

* Low network latency
* Reduced data movement
* Faster response for latency-sensitive applications
* Local processing

Important clarification:

> Edge does not necessarily mean weak hardware.

An edge node can have substantial CPU, RAM, or GPU capacity.

---

## 4.2 Cloud

Cloud infrastructure consists of centralized computing resources, generally deployed inside large data centers.

Advantages:

* Large compute capacity
* Large memory capacity
* Powerful GPUs
* Large-scale storage
* High scalability
* Centralized management

Potential disadvantages for latency-sensitive workloads:

* Greater network distance
* Network transmission delay
* Possible congestion
* Data-transfer costs

Important clarification:

> Cloud is not inherently "slow."

Cloud servers can be extremely fast computationally. The issue is that end-to-end response time can increase because the request may need to travel farther through the network.

---

# 5. WHY BOTH EDGE AND CLOUD EXIST

Neither environment is universally superior.

Example:

```text
EDGE A
CPU: 90%
Latency: 8ms
Cost: Medium

EDGE B
CPU: 40%
Latency: 10ms
Cost: Low

CLOUD
CPU: 25%
Latency: 25ms
Cost: High
```

Depending on the workload and its SLA, different locations may be optimal.

Therefore the system should not permanently prefer:

* Edge
* Cloud
* The closest node
* The most powerful node
* The cheapest node

Instead, it must dynamically evaluate the available choices.

---

# 6. THE ACTUAL PROBLEM

The core problem is:

> **Static workload placement cannot effectively adapt to continuously changing traffic, infrastructure utilization, network conditions, energy consumption, operational cost, and reliability.**

A workload can begin in a healthy state:

```text
CPU: 35%
Latency: 8ms
Traffic: Normal
SLA: Satisfied
```

Then traffic increases:

```text
CPU: 95%
Latency: 30ms
Traffic: Extremely High
SLA: Violated
```

At the same time, another node may be available:

```text
CPU: 35%
Latency: 10ms
```

The system therefore needs to dynamically reconsider the workload's location.

---

# 7. WHY "MOVE EVERYTHING TO THE CLOUD" DOES NOT SOLVE THE PROBLEM

A naive solution would be:

```text
Edge overloaded
       |
       v
Move to cloud
```

This is insufficient because the cloud may introduce:

* Higher network latency
* Higher bandwidth usage
* Higher operational cost
* Higher energy consumption
* Data-transfer overhead
* Possible SLA violations

Likewise, keeping everything at the edge can cause:

* Edge resource exhaustion
* Higher infrastructure cost
* High energy consumption
* Poor utilization
* Capacity limitations

Therefore the actual goal is not:

> Edge vs Cloud.

It is:

> **Find the best placement for each workload under current conditions.**

---

# 8. WHY THE PROBLEM IS MULTI-OBJECTIVE

The placement decision must consider several objectives simultaneously.

Primary objectives:

1. Minimize latency
2. Avoid resource overload
3. Minimize cost
4. Minimize energy consumption
5. Maintain reliability
6. Respect capacity constraints
7. Maintain SLA requirements
8. Anticipate future workload conditions

The system therefore performs a trade-off.

For example:

```text
Node A
Low latency
High CPU
High energy

Node B
Moderate latency
Low CPU
Low energy

Cloud
High latency
Very high capacity
High cost
```

There is no universally optimal choice.

The correct choice depends on the workload and current conditions.

# 9. NGINX VS THIS PROJECT

This distinction is a fundamental project concept.

## Nginx

Nginx primarily operates at the request level.

Example:

```text
User Request
      |
      v
    NGINX
   /  |  \
  v   v   v
App A App B App C
```

Nginx decides:

> **Which already-running application instance should handle this request?**

---

## PS-S04 Orchestrator

The proposed system operates at the workload/infrastructure level.

Example:

```text
Application X
      |
      +---- Edge A
      +---- Edge B
      +---- Cloud
```

The orchestrator decides:

> **Where should Application X itself be deployed or running?**

It can instruct the infrastructure layer to:

* Deploy
* Reschedule
* Scale
* Migrate
* Redistribute

Therefore:

**Nginx = request routing**

**PS-S04 = workload placement and infrastructure orchestration**

They can coexist.

## Component 2: Adaptive Multi-Objective Optimizer

Purpose:

> **Decide where the workload should run.**

This is the most important algorithmic component.

The initial simple approach was a weighted score:

```text
Score =
w1 * Latency
+
w2 * Capacity
+
w3 * Cost
+
w4 * Energy
+
w5 * Reliability
```

However, this approach has limitations.

---

# 13. LIMITATIONS OF STATIC WEIGHTED SCORING

## Problem 1: Arbitrary weights

Someone must manually decide:

```text
Latency = 40%
Capacity = 25%
Cost = 15%
Energy = 10%
Reliability = 10%
```

These values are subjective.

Different workloads may require different priorities.

---

## Problem 2: No historical memory

A pure score may make a completely new decision every cycle.

Small metric fluctuations can cause:

```text
A -> B -> A -> B -> A
```

This is workload placement thrashing.

---

## Problem 3: Workload concentration

If ten workloads independently determine that Edge B is the best node, they may all move there simultaneously.

Result:

```text
Edge B
CPU = 100%
```

The optimizer has effectively created the overload it was supposed to prevent.

---

# 14. PROPOSED DIFFERENTIATOR: PHYSARUM-INSPIRED OPTIMIZATION

The project proposes a nature-inspired adaptive optimization mechanism based on the behavior of:

**Physarum polycephalum**

commonly known as slime mould.

The important biological principle is:

> **Successful paths become stronger; unsuccessful paths weaken and disappear.**

The organism does not require a centralized controller to determine the best route.

---

# 15. MAPPING PHYSARUM TO EDGE-CLOUD ORCHESTRATION

Biological concept:

```text
Food
 |
Paths
 |
Good path becomes stronger
Bad path becomes weaker
```

System concept:

```text
Workload
 |
Candidate infrastructure nodes
 |
Successful node becomes more attractive
Poor node becomes less attractive
```

Mapping:

| Physarum concept  | Project equivalent            |
| ----------------- | ----------------------------- |
| Food              | Suitable workload destination |
| Path              | Candidate compute node        |
| Tube thickness    | Node attractiveness           |
| Nutrient flow     | Successful workload execution |
| Reinforcement     | Good performance              |
| Decay             | Poor performance              |
| Exploration       | Trying alternatives           |
| Efficient network | Efficient workload placement  |

---

# 16. DIGITAL "PHEROMONE" / ATTRACTIVENESS

Each node maintains an adaptive value representing its historical suitability.

Example:

```text
Edge A = 50
Edge B = 75
Cloud  = 60
```

Higher value means:

> This node has historically been a good placement for this workload.

The value changes over time.

---

# 17. PHEROMONE UPDATE MODEL

Conceptually:

```text
P(t+1) =
P(t) * (1 - decay)
+
reinforcement
```

Meaning:

```text
New attractiveness
=
old attractiveness
-
decay
+
reward for good performance
```

If a node performs well:

```text
Previous = 70
Decay = 7
Reward = 15

New = 70 - 7 + 15
New = 78
```

If a node performs badly:

```text
Previous = 70
Decay = 7
Reward = 0

New = 63
```

Thus the node gradually loses attractiveness.

---

# 18. WHAT COUNTS AS GOOD PERFORMANCE?

A node should receive stronger reinforcement when it demonstrates:

* Low latency
* Acceptable CPU utilization
* Acceptable RAM utilization
* Sufficient capacity
* Low cost
* Low energy consumption
* High reliability
* SLA satisfaction
* Healthy network conditions

A conceptual reinforcement function can be based on:

```text
Reinforcement ∝
1 / (
1
+
normalized latency
+
normalized CPU
+
normalized cost
+
normalized energy
)
```

The exact implementation should be experimentally tuned.

Important:

> The algorithm still requires parameter selection. Physarum-inspired adaptation does not magically remove all design parameters.

Its advantage is that it introduces **memory, gradual adaptation, and reinforcement/decay behavior** rather than relying entirely on a fixed winner-takes-all score.

---

# 19. HYSTERESIS / ANTI-THRASHING BEHAVIOR

Suppose Edge B has:

```text
Pheromone = 90
```

One temporary bad reading occurs.

Instead of instantly abandoning Edge B:

```text
90 -> 0
```

the system might perform:

```text
90 -> 81
```

If the node continues performing badly:

```text
81 -> 73 -> 66 -> 59
```

Eventually another node becomes more attractive.

This creates a form of memory.

The system therefore becomes less sensitive to small temporary fluctuations.

---

# 20. LOAD SPREADING

Multiple workloads should not blindly choose the same node.

The system can incorporate:

* Current load
* Pheromone
* Capacity constraints
* Exploration
* Randomized tie-breaking
* Per-node resource availability

This can distribute workloads across:

```text
Edge A
Edge B
Cloud
```

instead of causing:

```text
Everything -> Edge B
```

The purpose is to predict:

* Future request rate

```text
10:05 -> 2,000
10:10 -> 4,000
10:15 -> 8,000
```

The system predicts:

> Traffic is likely to exceed current capacity soon.

Instead of waiting for failure:

```text

```

the system can:

```text

```

# 23. SLA ENGINE

The SLA engine defines hard performance requirements.

Example:

```text
Maximum latency = 20ms
```

Possible policies:

```text
IF latency > 20ms
    trigger optimization

IF CPU > 85%
    evaluate redistribution

IF predicted CPU > 90%
    proactively scale

IF node reliability < threshold
    avoid node
```

The SLA engine therefore provides the system with explicit constraints.

# 40. RISKS

## Risk 1: Migration does not work

Fallback:

Use Kubernetes rescheduling or replica scaling.

---

## Risk 2: Kubernetes setup consumes too much time

Fallback:

Build a simulated node environment while keeping the orchestration logic real.

---

## Risk 3: Physarum algorithm becomes unstable

Fallback:

Use weighted scoring as a baseline/fallback optimizer.

---

## Risk 4: Prediction model is unreliable

Fallback:

Use reactive threshold-based orchestration and present prediction as an extension.

---

## Risk 5: Dashboard fails

Fallback:

Use backend logs and CLI visualization.

The underlying orchestration system must remain independent of the dashboard.

The Kubernetes/K3s layer performs the infrastructure action.

**An adaptive, multi-objective, nature-inspired Edge-Core workload orchestration platform capable of responding to changing traffic and infrastructure conditions through intelligent workload placement, migration, and scaling.**
